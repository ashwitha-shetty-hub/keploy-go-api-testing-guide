## How Keploy fits into the workflow

The useful part of Keploy in this example is the **record-and-replay workflow**.

Instead of manually writing every regression scenario first, you can exercise the API normally and record the interactions generated by those requests.

In this application, the `/create` endpoint does more than return an HTTP response. It also writes data to MySQL.

So there are two pieces of behavior involved:

1. The HTTP request and response.
2. The database interaction behind that request.

During recording, Keploy captures both kinds of interactions.

<RecordReplayDiagram />

The important part is that the HTTP interaction and the database behavior need to remain consistent during replay.

---

## Why start with a real API?

A record-and-replay workflow is easier to understand when you first establish that the application itself works.

If the API is already broken before recording starts, a later test failure becomes difficult to diagnose.

So the walkthrough follows a simple rule:

> **Verify the application first. Record second. Replay third.**

That gives you a known-good starting point.

<Steps>

<Step number={1} title="Start the Go application">

The sample used here is a Go URL-shortener backed by MySQL.

The application is containerized so that the Go service and its database can communicate through a Docker network.

Before introducing Keploy, make sure the application can start and respond to a request.

### Build the application image

From the project directory:

```bash
docker build -t url-short .
```

This creates the Docker image used to run the Go application.

### Create the Docker network

The Go application and MySQL container need to communicate with each other through the same Docker network.

Create the network first:

```bash
docker network create keploy-network
```

You only need to create this network once. The MySQL and Go application containers can then be started on the same network.

### Start MySQL

The application expects MySQL to be reachable through the `keploy-network` Docker network.

Start the database with:

```bash
docker run -p 3306:3306 --rm --name mysql --network keploy-network \
  -e MYSQL_ROOT_PASSWORD=my-secret-pw \
  -d mysql:latest
```

### Start the Go application

Run the application on the same Docker network:

```bash
docker run -p 8080:8080 --name urlshort --rm \
  --network keploy-network \
  url-short:latest
```

You should now have the MySQL and Go application containers running.

  src="/images/docker-containers.png"

  caption="The MySQL and Go application containers are running before recording starts."
/>

### Verify the application before recording

Before starting Keploy, make a normal request to the API.

For example:

```text
GET /all
```

The application returned:

```text
200
{"message":null,"status":true}
```

<Screenshot
  src="/images/api-baseline.png"
  alt="Successful GET request to the Go application's all endpoint"
  caption="A successful /all request establishes that the application is responding before Keploy records any traffic."
/>

This check matters because it gives you a baseline.

If this request fails, fix the application or its environment first. There is no value in debugging a Keploy test when the application itself has not been verified.

</Step>

<Step number={2} title="Start recording with Keploy">

Once the application is running, start Keploy in recording mode.

```bash
keploy record \
  -c "docker run --name urlshort --network keploy-network -p 8080:8080 url-short:latest" \
  --cmd-type docker-run \
  --network-name keploy-network
```

Keep the recording process running while you send requests to the application.

The important change is that your normal API traffic is now being captured for later replay.

<Screenshot
  src="/images/keploy-recording.png"
  alt="Keploy recording the Go API interaction in the terminal"
  caption="Keploy is running in record mode while the application receives API traffic."
/>

</Step>

<Step number={3} title="Generate API traffic">

The `/create` endpoint creates a shortened link and writes the original URL to MySQL.

A request can be sent with:

```bash
curl -i -X POST http://localhost:8080/create \
  -H 'Content-Type: application/json' \
  --data '{ "link": "https://github.com" }'
```

The request is not just an HTTP operation.

Behind it, the application performs a database insert.

That database interaction is part of what makes this example useful for understanding Keploy mocks.

</Step>

<Step number={4} title="Inspect what was recorded">

After recording, Keploy creates a test set containing the captured interactions.

The generated data includes both API tests and mocks.

For the database interaction, the recorded MySQL mock contained the SQL operation:

```yaml
version: api.keploy.io/v1beta1
kind: MySQL
name: mock-5
spec:
  metadata:
    connID: "0"
    destAddr: 172.18.0.2:3306
    requestOperation: COM_QUERY
    responseOperation: OK
    type: mocks
  requests:
    - header:
        header:
          payload_length: 56
          sequence_id: 0
        packet_type: COM_QUERY
      message:
        command: 3
        parameter_count: 0
        null_bitmap: []
        new_params_bind_flag: 0
        parameters: []
        query: insert into list (website) values("https://github.com")
  responses:
    - header:
        header:
          payload_length: 7
          sequence_id: 1
```

/>

This is useful because you can see the database operation that occurred during the API request rather than treating the API response as an isolated event.

</Step>

<Step number={5} title="If you encounter 100 Continue">

The first recording exposed an issue that was not obvious from the API itself.

One generated test contained:

```yaml
id: ...
req:
  header:
    Expect: 100-continue
resp:
  status_code: 100
  body: ""
  status_message: Continue
```

The test was:

```text
post-create-1
```

and it failed during replay.

The important clue was the `Expect: 100-continue` header.

<Screenshot
  src="/images/failed-100-continue.png"
  alt="Keploy test showing the failed post-create test caused by an HTTP 100 Continue interaction"
  caption="The first recording captured an intermediate 100 Continue interaction, which caused the recorded test to fail during replay."
/>

<Callout title="If you encounter this issue">
  If a recorded request contains an intermediate HTTP 100 Continue response,
  check how the original request was generated before changing the application
  or Keploy configuration.
</Callout>

In this case, the request had originally been sent from PowerShell.

The recording captured the intermediate `100 Continue` interaction, while the intended API behavior was the successful `200` response.

### Record the intended request again

Rather than modifying the generated test by hand, record the intended request again using `curl`.

The recording command remained:

```bash
keploy record \
  -c "docker run --name urlshort --network keploy-network -p 8080:8080 url-short:latest" \
  --cmd-type docker-run \
  --network-name keploy-network
```

Then send the API request with:

```bash
curl -i -X POST http://localhost:8080/create \
  -H 'Content-Type: application/json' \
  --data '{ "link": "https://github.com" }'
```

The clean recording produced a normal `200` response:

```text
{"message":"Converted","link":"http://localhost:8080/links/1","status":true}
```

There was no `Expect: 100-continue` header in this recording.

</Step>

<Step number={6} title="Keep the HTTP test and database mock consistent">

There is another important detail when working with recorded data.

The API response from `/create` contains the generated link ID.

For example:

```text
http://localhost:8080/links/1
```

That value is related to what the database returns from the insert operation.

During one attempt, the HTTP test from a fresh recording expected:

```text
/links/3
```

but the existing MySQL mock returned:

```yaml
last_insert_id: 1
```

The HTTP interaction and database mock therefore described different states.

The replay failed because those recorded pieces no longer agreed.

<Callout title="If you encounter this issue">
  When a recorded API response contains data generated by the database, check
  that the database mock produces the same value expected by the HTTP test.
</Callout>

This is why blindly copying a single recorded HTTP test into an older test set can cause unexpected failures.

</Step>

<Step number={7} title="Reset the database and record from a clean state">

To make the recording deterministic, the MySQL container was removed:

```bash
docker rm -f mysql
```

Then MySQL was started again:

```bash
docker run -p 3306:3306 --rm --name mysql --network keploy-network \
  -e MYSQL_ROOT_PASSWORD=my-secret-pw \
  -d mysql:latest
```

After the fresh database was ready, the `/create` request was recorded again with `curl`.

This produced a clean test where the generated ID started from the fresh database state.

The resulting HTTP response was:

```text
{"message":"Converted","link":"http://localhost:8080/links/1","status":true}
```

The important lesson is not the number `1` itself.

It is that the **database state used while recording needs to match the state represented by the recorded mocks during replay**.

</Step>

<Step number={8} title="Replay the recorded tests">

Once the test and mock data were consistent, replay the test set.

```bash
keploy test \
  -c "docker run --name urlshort --network keploy-network -p 8080:8080 url-short:latest" \
  --cmd-type docker-run \
  --network-name keploy-network \
  --delay 10 \
  --path /mnt/c/Users/HP/samples-go/mux-mysql \
  --test-sets test-set-0
```

Keploy replayed four tests.

The final result was:

```text
TESTRUN SUMMARY. For test-set: "test-set-0"
Total tests: 4
Total test passed: 4
Total test failed: 0
```

<Screenshot
  src="/images/replay-success.png"
  alt="Keploy test run showing four tests passed and zero tests failed"
  caption="The final test-set-0 replay completed successfully: 4 tests passed and 0 tests failed."
/>

The replay succeeded after the recorded HTTP interaction and database mock were brought back to the same database state.

</Step>

</Steps>

## Troubleshooting checklist

When a recorded test fails, avoid changing multiple things at once.

Work through the interaction in order.

### The test contains `100 Continue`

Check the request headers.

If you see:

```text
Expect: 100-continue
```

look at how the original request was generated.

In this walkthrough, the request had been sent from PowerShell. Recording the intended request again with `curl` produced the clean interaction.

### The HTTP response does not match replay

Check whether the response contains a value generated by the database.

For `/create`, the generated link ID is an example.

Then inspect the corresponding database mock.

### The database mock returns a different value

Check the recorded MySQL response.

For example, if the HTTP test expects an ID corresponding to one database state while the mock returns another, the two recorded interactions are inconsistent.

A clean database and a fresh recording can remove that mismatch.

### The application itself does not respond

Go back to the baseline.

Verify that:

```text
MySQL
  ↓
Go application
  ↓
API request
```

works before troubleshooting the recorded test.

## What to take away

The most useful lesson from this workflow is that record-and-replay testing is not only about capturing HTTP traffic.

For an API that depends on a database, the recorded database interaction can be just as important as the HTTP request and response.

A practical workflow is:

```text
1. Start the dependencies
2. Verify the application
3. Record real traffic
4. Inspect the generated tests
5. Inspect the database mocks
6. Fix inconsistencies at the source
7. Replay the complete test set
```

When something fails, inspect the recorded interaction before changing the application.

That makes the debugging process much more deliberate.
